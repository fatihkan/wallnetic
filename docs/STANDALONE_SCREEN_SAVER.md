# Standalone screen saver candidate

Implementation: [#274](https://github.com/fatihkan/wallnetic/issues/274), following
the [#259 feasibility decision](SCREENSAVER_FEASIBILITY.md).

**Status: development candidate, distribution deferred.** This is a separately
built `.saver`, not part of the Wallnetic app or its Store/DMG release. The
candidate uses `com.wallnetic.screensaver`, version **0.1.0 (1)**, independently
of the application's version. Its deployment target is macOS 13 and both native
arm64/x86_64 slices are built. Neither the OS floor nor physical Intel operation
has been certified by the current local tests.

## Behavior and scope

Each view owns one muted AVQueuePlayer, one AVPlayerLooper and one aspect-fill
AVPlayerLayer. The preview uses Lagoon; a full-size activation picks Lagoon or
Ember independently for that view and loops that selection. There is no media
rotation within an activation and no settings, network, external video paths,
App Group, main-app dependency, installer or wallpaper/lock policy modification.

The two original videos are H.264, 1280 × 720, 30 fps, six seconds and silent.
Together they occupy **690,598 bytes**. They were generated by the repository's
`tools/generate-wallpaper-pack.swift`; the source, outputs and companion use the
MIT license. [Provenance and hashes](../catalog/media/README.md) are copied into
the bundle with the license. The build checks exact lengths and SHA-256 hashes.
Changing the assets requires an intentional manifest update. There are no media
downloads or package-manager dependencies.

Runtime reads only the two fixed resource names. Missing, empty, oversized
(over 2 MiB), symlinked or undecodable media yields a black view and releases all
playback references. A one-second public `animateOneFrame` callback checks decode
status and gives a non-advancing player a 15-second limit. A failed activation
stays black until an explicit stop/start; duplicate starts and wake callbacks
do not trigger a retry loop. The OS must supply its documented callbacks for
this supervision to run. [ScreenSaverView animation callback](https://developer.apple.com/documentation/screensaver/screensaverview/animateoneframe()).

Stop, view detachment and either display/system sleep release the player, looper,
items and layer. System sleep and display sleep are tracked separately; waking
one does not override the other. Only an attached, still-requested view may
resume. Playback never prevents display sleep. Multiple views do not share
playback state, so stopping a preview cannot pause another display.

These limits bound bundled content, player count and retry behavior; they are
not a hard cap on AVFoundation's memory, decode surfaces, GPU work or the OS host.
Actual resource usage grows with the number and resolution of active views.
Host lifecycle defects cannot be solved by this view alone.

## Build and checks

From the repository root, on a Mac with Xcode command-line tools:

```sh
tools/screensaver/build.sh                  # optimized universal local bundle
tools/screensaver-probe/build.sh --run      # candidate + ordinary-window checks
tools/screensaver-probe/build.sh --benchmark # also measure debug-host CPU/footprint
```

Each command builds a new ignored `.build/screensaver-candidate.XXXXXX` directory.
It does not install a screen saver, select it, invoke Apple's system host, alter
security settings, put the Mac to sleep or lock it. The separate test host loads
the actual compiled candidate; it contains no second implementation. It is only
for trusted local builds, not arbitrary downloaded bundles. It emulates the
public animation callback while AVFoundation decodes and presents real video.

`tools/screensaver/validate.py` verifies the resource manifest, license presence,
bundle identity, payload, native architectures, deployment target, system library
dependencies, signature and absence of entitlements. `--distribution` additionally
requires a Developer ID Application signature, hardened runtime and timestamp;
an ad-hoc local build is rejected. CI runs the windowed checks, bad-media copies
and packaging rejection cases before the existing application test suite.

## Signing and packaging

The separate packaging command requires an explicitly supplied signing identity
and an already configured notarytool Keychain profile. It rebuilds from source,
signs and validates the candidate, creates and signs a DMG, submits that DMG to
Apple, requires an accepted result, staples and validates its ticket, verifies
the image and performs a Gatekeeper assessment. It records the submission result
and SHA-256 locally. It neither publishes an artifact nor installs the companion.

```sh
tools/screensaver/package.sh \
  --identity 'Developer ID Application: YOUR IDENTITY' \
  --notary-profile YOUR_KEYCHAIN_PROFILE
```

Do not put passwords, private keys or signing-team values in source control.
This command is deliberately separate from automatic CI and the application's
release workflow. Its successful end-to-end execution is **not yet validated**;
the local checks establish ad-hoc builds and rejection of invalid payloads only.
The exact signed artifact must pass the fresh-download and OS/device matrix
below before distribution. The public workflow supports notarizing nested code
inside a DMG and stapling the DMG's ticket.
[Apple's notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).

## Installation, update and removal

[INSTALL.txt](../tools/screensaver/INSTALL.txt) is included in the candidate DMG.
For an approved signed artifact, use the system screen-saver installation flow
and prefer current-user installation. The user selects it in System Settings.
Before update or removal, choose a different saver, then replace/remove only
`WallneticScreenSaver.saver`. Confirm the new or replacement saver actually loads;
a cached old host is a failed validation, not justification to kill a system
process or edit private preferences. These instructions still need actual OS
validation. They do not authorize automated installation during development.

The companion keeps no external media or preferences, and does not change the
desktop image. Removing it requires no Wallnetic-library cleanup. Existing
still-frame sync remains separate: disabling it in Wallnetic attempts to restore
its saved images, subject to the limitations in the feasibility record. The
companion does not provide live video behind the secure lock/login UI.

## Evidence and release decision

Observed **2026-10-12**, local Apple Silicon, macOS 26.6.2 (25G83), Xcode 26.4
(17E192), macOS 26.4 SDK; ordinary windows, ad-hoc signature:

- 26 normal playback/lifecycle assertions passed, including two decoding views,
  complete loops, mute/sleep policy, portrait resizing, independent stop,
  overlapping synthetic system/display sleep, detachment/reattachment, 20 repeated
  start/stop cycles, deallocation of both unused and used views, a stalled-player
  timeout, prevention of retries and recovery after explicit stop/start.
- Five bad-media scenarios (missing, empty, corrupt, oversized, symlink) each
  passed four fallback/release/no-retry assertions: **46 runtime assertions total**.
- **Nine packaging rejection checks** passed: ad-hoc distribution, the five
  bad-media variants, changed identifier, extra executable, missing license.
- Candidate and host compile for both architectures with warnings treated as
  errors. Real Intel runtime is untested. The application target is untouched.

One short debug-host measurement (one CPU core = 100%; physical process footprint,
not total decoder/GPU memory):

| Phase | Duration | Host CPU | Footprint at end |
| --- | ---: | ---: | ---: |
| Two idle windows before playback | 8.01 s | 1.747% | 14,205,648 bytes |
| Two playing windows | 15.01 s | 4.392% | 18,170,600 bytes |
| Both stopped, after lifecycle checks | 8.01 s | 1.896% | 20,726,504 bytes |

CPU returned near the host's own event-pump baseline. The footprint remains above
the cold baseline after decoder/AppKit use; this is not proof of zero retained
system buffers or a long-run memory plateau. Tests establish cleared references
and view deallocation. GPU, energy, decoder-service memory and thermal costs
were **not measured**. These numbers are an isolated-host observation, not a
screen-saver power benchmark or a physical multi-display result.

**Release decision: defer distribution.** Keep #274 open until these gates have
recorded evidence:

| Gate | Current evidence / remaining work |
| --- | --- |
| Apple's actual screen-saver host | Not run; preview, full-screen and idle activation required |
| OS/architecture support | Universal compile only; physical macOS 13 and current OS, Intel and Apple Silicon required |
| Display topology | Two ordinary windows tested; real independent/mirrored displays, reconnect and resize required |
| Power, lock and sessions | Synthetic notifications tested; physical display/system sleep, wake, lock/unlock, fast user switching required |
| Resource behavior | Local reference release/CPU/footprint observed; long-run actual-host CPU/GPU/memory/energy and dismissal required |
| Signing and notarization | Packaging commands prepared; real Developer ID, accepted notarization, ticket and fresh-download Gatekeeper checks required |
| Install/update/removal | Instructions prepared; actual user-scoped installation, new-build host reload and replacement/removal required |

If lifecycle callbacks or the documented host behavior fail without a public
mitigation, narrow support or defer the feature. Do not add private notifications,
host-process termination, elevated helpers, quarantine removal or security
exceptions to meet a release date.
